# GUI 拖动与合成性能

窗口拖动使用输入事件的原始双轴像素位移。标题栏在左键按下时获取拖动状态，保持至释放或窗口销毁；窗口位置和鼠标位置使用同一份位移。窗口 X 坐标无需按 4 像素对齐：按报告舍入会丢弃连续的 ±1 像素移动，并让左右移动出现不对称。USB 高频小位移报告尤其容易触发这一问题。

## 合成路径

`apps/gui/sheet.h` 定义独立的图层接口，`sheet.c` 不依赖 GUI RPC 或输入接口。像素归属仍使用稳定的图层指针，显示仍遵循实际 stride 和 RGB 位序。
可见图层更换尺寸或缓冲时，`sheet_setbuf` 对新旧范围一次重新合成，保持层序并恢复缩小后暴露的像素；宿主校验覆盖透明、遮挡、隐藏和屏外图层的随机缩放。

移动图层时，位置不变立即返回；位置变化后，新区域完整合成一次，旧区域仅合成新区域没有覆盖的部分。矩形相交时，旧位置露出的部分至多分成四个不重叠条带；不相交时重绘两个独立矩形。透明图层的新区域同样完整合成，以恢复透明像素下方的窗口。

旧实现对旧、新两个矩形分别完整重建归属并写屏，重复处理相交区域。旧矩形包含露出的背景时，未归属像素还会让算法继续遍历下方各层，即使这些层的大部分已经被覆盖。分离露出条带既减少重复写屏，也减少这些无效扫描。鼠标按钮事件产生的零位移不再触发两次光标合成。

局部绘图的 `window_present` 继续复制 damage 到独立的已提交平面，`window_refresh` 保留异步 damage 合并。这样原有绘图指针可持续用于增量更新，遮挡恢复不会读取正在绘制的半帧。下方图层移动基准没有改变普通内容刷新；完整帧的所有权交换见下一节。

## 整帧提交与所有权

远程窗口的事件区和两个像素平面共用一个 VM 区域，两个平面的像素存储互不重叠。
窗口构造直接使用其中一个平面，避免分配临时的私有整帧再替换。服务端记录 `front`，
客户端只可写另一块平面；帧 RPC 校验窗口 ID、owner TID/generation 和提交的平面索引。
客户端共享元数据不能改变服务端的 `front`。映射大小包括两个平面并检查乘法、加法、
页对齐及共享地址区容量；客户端的地址区用量增加，但稳定状态下的像素存储仍为两份。

`window_present_frame(window, first, last)` 面向完整覆盖指定矩形的生产者：

1. 使用 `window_get_buffer` 获取当前绘图平面，按实际 pitch 完整写入提交矩形。
2. 同步提交。服务端保留矩形外的已提交像素（包括当前窗口装饰），将图层的图像指针
   切到新平面，完成显示后应答。当前矩形及待处理的异步 damage 合并消费。
3. 应答后重新获取绘图平面，原来的绘图指针失效。交还的平面保存较老的帧，
   下一次整帧提交必须重新绘制目标矩形，不能假定它含有上一帧的增量绘图结果。

平面的不可修改性由所有权协议约束，不是在每帧切换跨进程页权限；继续使用失效指针
属于客户端错误。空矩形不进行交换。若帧 RPC 失败或应答不完整，客户端停止交出任何
绘图指针，保留窗口 ID 供关闭清理，避免在提交结果不确定时误写服务端持有的平面。
连接建立或参数检查在提交前失败时不发生所有权变化。普通复制提交和帧交换必须由
窗口 owner 串行调用，不能与同一窗口的绘图并发。

关闭时先解除客户端映射，服务端移除图层后释放自己的整个 VM 区域；不能单独释放
位于区域内部的当前像素指针。owner 退出时按 TID/generation 回收窗口和两块平面，
其他地址空间持有的共享页引用由正式 VM API 处理。

EGL 每帧获取新绘图平面并调用此接口。原来三段图像搬运中的“GUI 绘图平面 → 已提交
整帧”被指针交换取代；Mesa 颜色资源 → GUI 绘图平面、可见区域 → framebuffer
仍需要复制，客户端区域之外仍需保存装饰。Vulkan WSI、SDL 软件 surface 和 term
继续使用适合增量更新的复制提交。

这项改动减少整帧复制及 GUI 临界区内的工作量；它没有异步提交队列，渲染和显示仍
在 swap 边界串行，GUI 的 `TaskLock()` 粒度和逐像素归属扫描也没有改变。

### 系统内验证与基准

```sh
python3 scripts/test-x86_64.py --gui-frames --accel kvm --cpu host --memory 3072
python3 scripts/test-x86_64.py --arch i386 --gui-frames --accel kvm --cpu host --memory 512
```

`guitest.bin frames` 使用 648×428 窗口、640×400 客户区，交替顺序比较复制提交与
帧交换，各三轮、每轮 240 帧。分别记录完整填色与提交耗时和提交阶段耗时；两种模式
都填完整客户区，均等待实际显示应答，截图与输入等待不计入计时。

实际像素检查覆盖连续平面交接、下一块平面整块写入紫色后的鼠标恢复/遮挡恢复、
窗口装饰保持、复制与异步局部更新混用，以及携带已提交窗口的子进程直接退出后的
owner 回收。宿主对客户区的所有像素和整个窗口装饰做比较，通过键盘事件推进阶段。

llvmpipe 的端到端对照使用已有 glxgears 固定几何、300×300 客户区、预热 180 帧，
随后三轮各 3600 帧。新增比较工具保留各轮数据，并检查 CPU、worker、窗口尺寸和
完整 QEMU 配置一致性：

```sh
python3 scripts/test-x86_64.py --gears-bench --accel kvm --cpu host \
  --cpus 4 --memory 3072 --out /tmp/gears-after
python3 scripts/compare-gears.py --before /tmp/gears-before /tmp/gears-before2 \
  --after /tmp/gears-after /tmp/gears-after2 --output /tmp/gears-comparison.json
```

2026-09-09，Intel Core Ultra 7 270K Plus / WSL2，同一 QEMU 10.2.1 KVM
配置（BIOS、`-cpu host -smp 4 -m 3072`）。基线为 `42ba5e4`，修改前后各两次
冷启动、累计六轮，按累计帧数与累计时间汇总：

| glxgears 指标 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| 总 FPS | 2941.706 | 3113.520 | +5.84% |
| 总时间 µs/帧 | 339.939 | 321.180 | −5.52% |
| 绘制 µs/帧 | 242.376 | 236.961 | −2.23% |
| 同步呈现 µs/帧 | 96.056 | 82.778 | −13.82% |

光栅器、worker 策略、几何和基准程序保持一致；绘制阶段的小幅波动不能当成
光栅算法优化。同步呈现计时包括 EGL 映射/复制、RPC 与 GUI 显示，不只是一次
`memcpy`。这里没有将丢帧或延迟呈现算成 FPS 提升。

640×400 客户区的系统内对照在相同的新版本上交替使用两种提交接口：x86_64
提交耗时从复制方式的 150.797 降到交换方式的 133.885 µs/帧；i386（同一 KVM
配置、512 MiB）从 142.884 降到 101.639 µs/帧。不同架构之间不直接比较性能。
各轮原始采样、参数和汇总保存在 [JSON](benchmarks/gui-frame-exchange.json)。

最终验证通过双架构完整应用构建、LiveCD 打包和 `--gui-frames`、`--sdl`，以及
x86_64 KVM 的 BIOS/UEFI `--opengl`。两帧 OpenGL 窗口像素分别匹配 GL 读回
`7fe5054d`、`e33873d8`，保持已有回归结果。测试后恢复正常启动配置和镜像。
尚未在真实 USB 鼠标或物理 framebuffer 上测量本次帧交换的收益。

## 可复现图层移动基准

```sh
# baseline 指定修改前的提交；默认 HEAD 适用于尚未提交的工作区修改。
taskset -c 0 python3 scripts/compare-gui.py \
  --baseline f963fe6043d415d50066b0191e9e47e1836979a8 --runs 7
```

脚本分别编译指定提交与工作区的实际 `sheet.c`，使用相同的独立测试驱动，不复制合成算法。旧版仅将 `gui.h` 包含替换为抽出的同一份图层声明。可用 `CC` 选择宿主 C 编译器；临时源码和可执行文件在结束后删除。

基准使用 1024×768 RAM framebuffer、640×400 被拖动窗口、16×19 透明光标，分别测试下方有 0 和 32 个被覆盖窗口的场景。每项执行 400 次；前后版本交替执行 7 轮，报告每操作耗时的中位数。移动场景在相邻像素间往返，包含水平、垂直、对角和光标移动；普通刷新为整窗口刷新。零位移返回时间接近计时下限，显示为 `no-op`，不计算夸大的倍数。

一次固定 CPU 0 的测量结果如下：Intel Core Ultra 7 270K Plus，Linux/Hyper-V 环境，GCC 15.2.0，`-O2 -std=gnu17`。单位为 µs/操作。

| 被覆盖窗口数 | 场景 | 修改前 | 修改后 | 加速比 |
| --- | --- | ---: | ---: | ---: |
| 0 | 水平移动 | 441.691 | 201.989 | 2.19× |
| 0 | 垂直移动 | 437.229 | 193.008 | 2.27× |
| 0 | 对角移动 | 441.576 | 202.281 | 2.18× |
| 0 | 光标移动 | 1.817 | 1.100 | 1.65× |
| 0 | 普通内容刷新 | 84.019 | 83.399 | 1.01× |
| 32 | 水平移动 | 1337.216 | 203.092 | 6.58× |
| 32 | 垂直移动 | 1333.066 | 192.249 | 6.93× |
| 32 | 对角移动 | 1328.024 | 201.744 | 6.58× |
| 32 | 光标移动 | 1.791 | 1.082 | 1.66× |
| 32 | 普通内容刷新 | 82.733 | 82.858 | 1.00× |

零位移原来约 381 µs，现在直接返回。这些数据证明合成算法的 CPU 工作量改善，不代表真实机器或 SDL/Vulkan/OpenGL 应用的端到端 FPS。宿主 RAM、memcpy 和执行环境不同于 Plant OS 的用户运行库及显存，不能直接将上述耗时倒数当成应用帧率。

## 正确性与输入回归

每轮基准均使用独立的逐像素、从后向前参考渲染器检查 framebuffer 和像素归属。确定性随机序列覆盖移动、远距离跳转、屏外裁剪、透明/不透明图层、层级变化、隐藏及销毁；分别检查 RGB/BGR 和带填充的 pitch，并确认行填充没有被覆盖。计时后的完整场景也进行像素校验。

可用宿主检查器验证同一源码：

```sh
cc -O1 -g -std=gnu17 -fsanitize=address,undefined -fno-omit-frame-pointer \
  -Iapps/gui apps/gui/sheet.c scripts/tests/gui-compositor.c \
  -o /tmp/plant-gui-sanitize
/tmp/plant-gui-sanitize
```

系统内回归通过 init.mst 启动程序，仅通过 QMP 发送真实相对位移和按钮事件。`--mouse` 和 `--usb` 在测试窗口标题栏按住左键，依次发送 8 个 +1 X、−1 X、+1 Y、−1 Y 报告，每段比较移动后窗口边框的实际像素，然后检查客户区按钮、滚轮和位置事件。截图保存为 `mouse-drag-*.ppm`。原先的逐报告舍入无法通过横向检查。

本次实际通过以下完整构建、LiveCD 打包和 QEMU TCG 冷启动回归（CPU `max`，4 核）：

```sh
python3 scripts/test-x86_64.py --mouse --memory 3072 --timeout 180
python3 scripts/test-x86_64.py --usb --memory 3072 --timeout 240
python3 scripts/test-x86_64.py --arch i386 --mouse --memory 512 --timeout 180
```

USB 专项还覆盖 USB 键盘、终端像素、热插拔及存储校验。测试脚本恢复正常启动配置并重新打包镜像。真实 USB 鼠标及物理显示器上的最终拖动体验尚需在目标机器确认。
